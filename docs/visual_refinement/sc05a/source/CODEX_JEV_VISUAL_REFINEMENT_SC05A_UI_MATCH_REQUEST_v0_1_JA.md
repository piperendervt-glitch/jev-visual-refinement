## 2．視覚基準と、画像どおりにしてはいけないもの

### 2.1 一致させるもの

左の画像プレビュー／情報欄、中央上の大きいパイプライン、右のJev・採用カード、中段の横棒付き評価表、下段の候補サムネイル・横向きタイムライン・ログを、基準画像と同じ配置にします。暗い紺色の面、シアンの細い境界、4laneの色帯、角丸、見出し・アイコン・行高・余白を合わせます。

**単に同じ項目があれば合格ではありません。** 現在の横長リストUIを色だけ変えたもの、別ページへ必要パネルを追い出したもの、全画面の基準画像を背景に貼ったものは未達です。表・ボタン・マスク・経路は実DOM/SVG/canvas等の操作可能な部品とします。

### 2.2 許容する相違を限定する

- 写真、マスク、モデル名、点数、時刻、利用量はデータです。画像内の仮値を実測として複製しません。写真部は現時点では合成Kを用い、枠・サイズ・比率は基準に合わせます。
- fixtureで検証し、`FIXTURE / 実GPU未使用 / 実Jev未接続`を常設します。GPU実行中などの虚偽表示はしません。モデル候補名を併記する場合は「予定・未実行」とし、実行中のfixture名と分けます。
- 基準画像のENet/Fast-SCNNはモデル採用の指示ではありません。承認された固定構成を表示し、セマンティックとインスタンスを黙って同じ比較へ混ぜません。
- 基準画像で省略されている共通測定は、各laneの出口に「正規化・測定」を示す小段等を設けて明示します。全lane完了待ちを追加しません。
- 主採用はQのみ。理由の「コストも良好」を採用原因に混ぜません。コストは診断欄です。
- OSのタイトルバー、ブラウザーの外枠、微小なフォント描画差は完全pixel一致の対象外です。主要パネルの欠落・位置違い・読めない文字をこの例外に含めません。

既存修復画面にある「A 安定」「I 一貫」は契約の意味と違います。**A＝曖昧さ・矛盾（高いほど大）、R＝追加処理の解決見込み、I＝観測目的への重要性、C＝コスト適合、Q＝分割適合性・主採用軸**へ表示を合わせます。返却済み数値や尺度の意味は反転させません。

## 3．レイアウトの実装基準

主比較条件はブラウザーの**コンテンツviewport 1536×1024 CSS px、zoom 100%**です。取得方法、実viewport、devicePixelRatioを記録します。OS外枠込みの画像を無理に同じサイズへ変形して比較しません。

次の座標は添付画像から読み取ったおおよその配置目安（x,y,w,h）であり、固定canvas実装を要求するものではありません。通常のgrid/flex等で同じ見え方を作ります。

|---|---|---|
| ヘッダー | 全幅、上端約48px | タイトル・説明・状態を整列 |
| 左：フレームビュー | 12,58,301,480 | 主画像、再生位置相当の表示、採用追従／手動閲覧の識別 |
| 左：フレーム情報 | 12,547,301,245 | 元時刻・K・run・根拠、前後K相当の表示欄 |
| 画像処理パイプライン模式図 | 322,58,1203,480 | 同一K→縦に並ぶ4本の独立lane→測定→Jev→選抜・主表示 |
| Jev評価結果一覧 | 322,548,1203,245 | 固定4行、候補小画像、Q/4軸の横棒＋数値、判定・理由 |
| 下：マスク結果プレビュー | 13,801,665,210 | 4候補の同サイズカード。クリックで手動閲覧 |
| 下：選抜タイムライン | 686,801,510,210 | 横方向に評価・採用・維持・根拠更新を表示 |
| 下：処理ログ | 1202,801,323,210 | 最新上、閲覧中のscrollを勝手に移動しない |

最初に主要領域の位置と比率を合わせ、その後に文字・色・アイコン・余白を調整します。1536×1024では上記の全主要パネルを初期画面で確認できる構成にします。参考の目安として主要パネル境界のずれを概ね12px以内へ詰め、意図した意味補正の箇所は明記します。この数値だけを満たして読みにくい画面を合格にはしません。

実際の利用環境に近い約1905×867でも追加確認します。こちらは厳密な相似拡大ではなく、主要情報を欠落させず、文字切れ・パネル重なり・不必要な画面全体の横スクロールがないことを確認します。画像・文字を非等方に引き伸ばしません。

本文や表の文字は通常13px前後を目安に読みやすくし、すべてを一画面に収めるために全体を極端に縮小しません。長い内部ID・英語enumは詳細へ回し、主表示は日本語の短い状態名にします。

## 4．今回動く必要があるものと、後段を待つもの

| 項目 | SC05Aでの扱い |
|---|---|
| 非同期表示 | 既存fixtureイベントから後着評価を自動反映。reloadや行クリックを更新条件にしない |
| 模式図 | 4lane名・phase・独立分岐・測定・評価・採用を表示。S→A→B→Cの直列矢印は禁止 |
| 白ドット | 実際に記録されたfixture遷移のFlowPulseを有限に再生。存在しない処理の常時アニメーションは禁止 |
| キュー | 段／lane、単位、scope、待機・実行・最古待機を表示。黄色/橙/赤と件数・状態名を併用 |
| 評価表 | Qだけを主採用として強調。Aは方向を説明。null・未評価・無効・旧根拠を0点にしない |
| 採用理由 | 現在の差と過去Decisionを分ける。現在非採用・以前採用・下限未達・未評価を区別 |
| タイムライン | 非採用・維持も記録にある分だけ表示。過去cursorと現在を区別。根拠更新はE0→E1と示す |
| プレビュー | 主採用追従、手動候補、過去表示を区別。新winnerで手動閲覧やfocusを奪わない |
| 終了済みrun | queueに残された終了時の未処理数は「終了時未処理」「停止済み」等と明記。今後進むlive待機に見せない。旧保存値は書き換えない |
| fixture操作 | E0を1件完了などの開発用ボタンは通常の主画面から小さな検証パネルへ移す。検査機能自体は残す |

| 実モデル・Jev | 接続しない。SC02〜04で実データを同じUIへ接続し、SC05Bで実運用条件を最終確認 |

Q/A/R/I/C、根拠、採用・閲覧状態は既存の公開投影から受け取ります。見た目のためにUI独自のwinner計算・採点・架空の時間を作りません。表示に必要な読取り投影や局所不具合の修正は対象内ですが、公開契約の意味を変える必要がある場合は変更箇所と影響だけをまとめて判断待ちへ分離します。

## 5．Codex内で閉じる反復・検証手順

1. 基準画像を実際に開き、現アプリを起動して同じviewportで撮影します。最初に足りないパネル・位置・比率・文字の違いを短い作業表へ記録します。
2. 大きい差から実装します。レイアウト→模式図と接続→評価表とサムネイル→タイムライン／ログ→色・文字の順を基本とし、安定した既存核は作り直しません。
3. 正式に利用可能なブラウザー操作経路で、各節目に実画面を再撮影し、基準と横並びで目視比較します。DOMに部品が存在するだけで視覚合格にしません。
4. 不一致を自分で列挙し、修正可能な差が残る間は次の修正へ進みます。小差の判断や通常テストの再実行を毎回利用者へ返しません。進捗報告は作業中の短い報告とし、そこで完了しません。
5. 視覚整合後、下記の状態シナリオを実行し、関係する自動試験・既存回帰・JavaScript構文等を確認します。失敗は原因を調べて同じチャットで直します。
6. 最終修正後にもう一度、全体画面・意味・動作を確認します。修正前のスクリーンショットを最終版の証拠に使いません。

基準画像との全画素差・単一の類似度だけを完了判定にしません。動的内容・合成原画と参考写真・文字描画差を分け、実部品の配置と可読性を重点比較します。同じfixture状態の前後比較は自動画像差分で補助できますが、比較対象や除外領域を後から都合よく変えません。

### 必須の状態シナリオ

- 画面接続後にAを暫定採用→S上位へ改訂→B下位で維持。表・画像・線の強調・タイムラインが同期する。
- B手動閲覧中に主winnerが更新してもB閲覧・focusを保持。「採用へ戻る」でのみ復帰する。
- E1発行待ちではE0を旧根拠と明示し、同候補の再評価後は根拠更新として表示する。
- 少数のfixtureで待機0、注意、混雑、満杯の見え方を確認。停止／Replayでは保存時点の数であることを示す。
- 過去cursorを選ぶと当時のwinnerだけを表示し、現在へ戻れる。
- 画像失敗時に主採用可視receiptを送らず、回復後の実適用だけを記録する。画面変更で既存の保護を壊さない。

静止画では白ドットの移動や自動更新の成立を証明できません。これらは実ブラウザーの操作結果として記録し、必要な短い動作記録はCodex側に保存します。

## 6．完成条件と停止条件

**完成は「見た目」「意味」「操作・回帰」のすべてが成立した場合だけ**です。

- 主要パネルの配置・比率・部品構成が第3節と基準画像に整合している。
- 4lane、測定経路、Jev／選抜カード、横棒評価、4候補プレビュー、横向きタイムライン、ログが揃っている。
- 通常表示に重なり・切れ・読めない文字がなく、許容した差以外の大きな差を未修正で残していない。
- 基準画像中の仮値・未実装機能を実績と表示せず、Q・各軸・採用・旧根拠・終了時の意味が正しい。
- 第5節の状態シナリオと影響回帰を確認し、所有プロセスの正常終了・保存復元を確認している。

**テストが通っただけ、一回起動しただけ、「おおむね似た」と自己評価しただけでは完了にしません。** 一方、権限拒否、利用量・既存profile上限、ユーザー停止、実ブラウザー経路の利用不能、実データ未接続では解決できない要求、具体的な契約矛盾は無視しません。その場合は`BLOCKED_NOT_COMPLETE`または`PARTIAL_NOT_COMPLETE`として、残差と原因をまとめて保存し、完了を装いません。

同じ失敗手順を新しい根拠なく無期限反復しません。利用制限や安全審査を自動で回避するループ、追加クレジット購入、モデルの無断変更はありません。Goal modeを使っていても同じ境界です。

モデル・依存・runtime・外部フォント等の新規取得0、実動画解析0、GPU推論0、実Jev0、アプリから外部API送信0、GitHub/push0。所有するloopbackと、利用者が許可した正式Codex／ブラウザー操作経路は使用範囲です。新しいtool権限をこの文書だけで成立させません。大きなフレームワーク追加は不要です。

## 8．提出は短い報告と少数画像だけ

**ChatGPTへのソース、テスト実装、全DOM、全ログ、多数JSONの転送は不要です。** コード確認・試験点検・原因切分け・修正はこのCodexチャット内で完結させます。

最後は、状態、branch/HEAD、試験成功・失敗・未確認、視覚基準の達成状況、意図した相違、正常終了・保存・保全、後段未実施を含む短い報告一つと、次の最大3枚を基本に提出します。

1. 基準と同じ1536×1024の完成全体画面（4候補の比較と採用・非採用が見える状態）。
2. 手動閲覧維持またはE1旧根拠の代表状態（同じUIで意味を確認）。
3. 混雑または横幅／高さ変更時の代表状態。

主要状態を撮るたびに利用者の確認待ちで止めません。途中証拠はCodex側の必要最小限に留めます。人間の最終画面レビュー前なので、成功時の提出状態は`SC05A_UI_IMPLEMENTED_PENDING_USER_REVIEW`。実データ未接続の項目はSC02〜04／SC05Bへ明記し、SC05全体やアプリ全体を完成と呼びません。SC02の依頼文・実装を続けて作成しません。
