## 1．第一ゴールと完成範囲

### 1.1 利用者ができること [U/D]

保存動画を選び、手動で選択した一時点、または保存済みのキーフレーム集合を解析する。同じ元フレームへ3〜4個のセグメンターを投入し、分割結果が返った順に測定・Jev評価へ進める。評価応答の完了順に、同条件の到着済み候補から現在の採用結果を選び、元時刻付きのフレームへ重畳する。

構成・アーキテクチャ・設定を保存して同じ動画に繰り返し適用できる。採用結果だけでなく全候補・評価・改訂・時間・失敗を残し、後のCodexによる構成比較へ渡せる。

### 1.2 含めるもの／含めないもの

| 区分 | 内容 |
|---|---|
| 第一完成物に必須 | 保存動画、選択キーフレーム、3〜4個の実セグメンター経路、共通マスク形式、ローカル測定、実Jev、非同期選抜、元フレームへの重畳、後着・新根拠による改訂、保存構成、反復実験、全run索引・比較出力、正常終了 |
| 比較対照として必要 | 単独モデル、三本／四本、全件待ち、非同期Jev、非同期の固定規則、一本除外の構成。全対照の大量実測を毎回の機能完成条件にはしない |
| 後段へ移す | フレーム間の同一個体対応、対象台帳、P2場面・関係マップ、OCR、意味・外見VLM、Jev後の追加認識、領域ごとの異種マスク合成、予算再配分による未着手jobの自動剪定 |
| 第一版の対象外 | ASR、会話・三場統合、元マップ可視性改善、実カメラ／マイク、本人認証、実機操作、遠隔worker、学習、自動コード生成、任意スクリプト実行、全フレーム連続追跡 |

**分割結果を測定する通常コードは、今回の範囲内。** 別の物体認識・OCRモデルを「測定」と呼んで追加しない。セグメンターが元来返す分類候補は来歴付き出力として保存できるが、別の分類器の導入を必須にしない。

### 1.3 三つの判定を分ける

1. **アプリ機能の成立**：実画像・複数実マスク・実Jev・選抜・表示・保存・反復が接続され、訂正機構の試験が通ること。
2. **実運用での改訂観測**：自然な実Jev応答で勝者交代が観測されたか。起きなければ`LIVE_REVISION_NOT_OBSERVED`。
3. **品質・遅延上の優位性**：独立した品質評価と時間・資源比較で改善があったか。

3が成立しなくても、結果と限界を記録できるアプリは完成し得る。1が欠けているのに、fixtureの見栄えや高い点数だけで完成とはしない。[S2 第13節]

## 3．比較課題・アーキテクチャ・速度帯

### 3.1 先に固定する比較課題 [D]

同じ動画だけでは比較条件が足りない。`TaskDefinition`で次を固定する。

| 項目 | 内容 |
|---|---|
| `task_id / version` | 目的・評価対象の版 |
| `task_family` | `INSTANCE_OBJECTS`／`CLASS_AGNOSTIC_MASKS`／`SEMANTIC_REGIONS` |
| `purpose` | 何を分けたいか。例えば物体ごとの切り出し、分類名によらない領域候補、種類別の面 |
| `scope` | 全画像または明示したROI。正解マスクを選別用ROIとして漏洩させない |
| `coverage_policy` | 背景、対象外カテゴリ、未分類、重複・包含をどう扱うか |
| `granularity_policy` | 物体全体／部位／種類領域のどれを目標にするか |
| `quality_protocol` | 評価可能な品質項目と人手確認・正解の有無。選抜入力とは別管理 |

セマンティック・インスタンス・任意マスクを、同じ型に変換しただけで同一課題として順位付けしない。異なる種類を混ぜる研究構成には`MIXED_TASK_EXPLORATORY`を付け、整合した比較群の優劣へ混ぜない。

### 3.2 S/A/B/Cの扱い [U/H]

帯は利用者が示した**候補編成用の予想ラベル**。当該PC・解像度・全マスク生成経路での速度順位は未確認である。SがAより遅くても、待ち時間や計測を加工して順序を合わせない。モデル名に`S`が含まれることとA帯等のラベルも別。

| 帯 | ユーザー提示の候補群（選定前の一覧） |
|---|---|
| S | ENet、Fast-SCNN、STDC1、小型BiSeNet、YOLO11n-seg／YOLOv8n-seg、FastSAM |
| A | PIDNet-S、DDRNet-slim、BiSeNetV2、STDC2、YOLO11s-seg／YOLOv8s-seg、RF-DETR-Seg-N/S、MobileSAM |
| B | PIDNet-M、通常DDRNet、YOLO11m-seg／YOLOv8m-seg、PIDNet-L |
| C | SAM2、より大きいSAM系、SegFormer-B2以上、DeepLabv3+、大型U-Net、Mask R-CNN、大型Mask2Former、元祖SAM ViT-H等 |

この一覧全件の導入・互換対応は第一版の完成条件ではない。公称FPS、精度の高低、VRAM、ライセンス、配布継続を本版で再検証しておらず、数値を確定値として採用しない。

### 3.3 初期構成の候補 [D/H・未選定]

| 比較群 | 構成案 | 制約 |
|---|---|---|
| 対象物インスタンス・四本 | S:YOLO11n-seg、A:YOLO11s-seg、B:YOLO11m-seg、C:Mask R-CNN | 重み・対象クラスを確認してそろえる。三つのYOLOを異なる独立原理と数えない |
| 分類名によらないマスク・三本 | S:FastSAM-s、A:MobileSAM、C:SAM2.1 | 全画像の自動マスク生成を比較する。点一個への応答時間と混ぜない。B枠は未使用 |
| セマンティック比較 | 同じ対象分野・ラベル定義の3〜4経路を別に選ぶ | 保存動画と学習対象の不一致を確認。道路向け重みを汎用物体用と仮定しない |

最初は一つの比較群だけを選び、その中で3経路以上を実働させる。四本UIと実行器は用意するが、四本の実確認は実際に四経路を導入した場合だけ報告する。四本を採用した計画で一本が動かない場合は、理由と残件を記録し、黙って三本合格へ変更しない。

同じbackendのサイズ・既定設定違いは同じadapterで扱う。異なるbackendの追加は公開契約へ接続する拡張とし、選抜核を作り直さない。

## 4．パイプラインと手順1〜10の対応

```text
保存動画／キーフレーム集合／不変の実験設定
                   ↓
           KeyframeRecord K（同じ画像bytes）
                   ├─ S枠の領域分割 ─┐
                   ├─ A枠の領域分割 ─┤
                   ├─ B枠の領域分割 ─┼─ 完成順にCandidateSetと共通測定
                   └─ C枠の領域分割 ─┘             ↓
                                            有限Jev評価キュー
                                                   ↓ 評価応答の完了順
                                  同条件の候補選抜／短い状態確定
                                                   ↓
                                  元キーフレームへの重畳・改訂履歴
                                                   ↑
                        追加測定 → 根拠新版 → 必要候補の再評価

全候補・全評価・時刻・設定・失敗 → 保存run → 同条件比較／Codex分析
```

| ユーザー手順 | 本版の実装契約 |
|---|---|
| 1 キーフレーム取得 | 指定時刻と実decode時刻を区別し、Kの画素hash・PTSを固定 |
| 2〜5 各帯から実行 | 使用する3〜4枠を一つのplanとして受付。前の推論の終了を次の投入条件にしない |
| 6 完成結果をJevへ | 正規化・最低限の共通測定後に候補単位で投入。全候補や高度な追加測定を待たない |
| 7 応答順に取得 | 送信順のfuture待ちを避け、完了通知から処理する |
| 8 高得点を採用 | 主表示は第9〜10節の分割適合性。ユーザーの4軸は意味を保って個別表示・比較 |
| 9 重畳表示 | 同じKのマスク一式。異なるモデルの部分マスクを混成しない |
| 10 新根拠で再評価 | 第8・11節の版更新。旧勝者も対象にし、旧版点数と新版点数を比較しない |

各モデルで必要な前処理・後処理は実施可能だが、すべて記録する。元画像を使い回すことと、過去runの推論結果を使い回すことは別。比較用の実測runで、cacheしたマスクを新規推論結果に見せない。

## 6．マスク正規化・adapter契約

### 6.1 adapterの役割

adapterは入力Kと固定設定を受け、raw出力、共通マスク形式、変換、実device、時刻、失敗状態を返す。モデル初期化、前処理、推論、後処理、closeの計測境界を持つ。入力にない動画の別時点、音声、過去の正解を参照しない。

出力種別はセマンティックlabel map、インスタンスmask群、分類名によらないmask提案群を区別する。ラベルmapから連結成分を抽出しても、正しい個体分割が得られたと宣言しない。

### 6.2 元画像への復元

座標は元フレームのpixel edge基準、boxは`[x0,y0,x1,y1)`。resize・letterbox・padding・rotation・cropの逆変換を記録する。離散maskの復元は定義済みの離散変換、確率mapからの二値化は閾値と順序を設定版に含める。UIのCSS拡大率で解析座標を変更しない。

raw出力と正規化出力を保存し、異なるmask集合を一つのlabel mapへ潰して重複・包含を失わない。背景、unknown、対象外クラスを別に保持する。全maskを一式として採用し、勝者の見栄えのためだけに後から一部を取り除かない。

### 6.3 完了・空結果・失敗

| 状態 | 意味 |
|---|---|
| `SUCCEEDED_NONEMPTY` | 有効なmask一式。正確さまでは意味しない |
| `SUCCEEDED_EMPTY` | 正常に処理し対象maskが0件。0件を例外・架空のmaskに変えない |
| `FAILED_FORMAT / FAILED_INFERENCE / OOM` | 不正形式・推論失敗・メモリ不足。0点候補として選抜しない |
| `CANCELLED / EXPIRED / OLD_GENERATION` | 取消し・期限・旧世代。後着しても現在へ復活させない |
| `OUTPUT_LIMIT_EXCEEDED` | 事前の出力容量を超過。黙った切捨てではなく明示的な状態 |

一式の完了が通常の候補単位であり、全経路の完了を待たない。将来のstreaming mask対応は別契約。途中maskを完成品と偽らない。boxを矩形で塗っただけのものとfixture maskは、実セグメンテーション実績に数えない。[S2 第7節]

## 7．Jevへ渡すローカル測定

### 7.1 共通測定 [D]

Jevに送るのは、定義された測定値・目的・不足情報である。画像bytes、mask配列、巨大なembedding、動画・音声は送らない。モデルの自信値を全モデル共通の確率に読み替えない。[S1 第8〜9節、S2 第7節]

| 測定群 | 初期の内容 | 解釈上の制限 |
|---|---|---|
| 構造 | mask数、面積比の分布、union被覆率、2枚以上の重複画素率 | 多い／広いだけで良質とはしない。包含を許す課題もある |
| 分割の形 | 連結成分数、極小成分の割合、穴の有無、box内占有率 | 自然に離れた／穴のある対象もある。疑いと形式不正を分ける |
| 原画との対応 | mask境界付近の画像変化、内外の色差、境界と固定した画像edgeの距離要約 | 模様・影も境界になり得る。正解評価ではなく代理指標 |
| 目的適合の材料 | task/ROI内の被覆、対象外領域、利用可能な予測ラベルの由来 | 外部正解や未実施の認識から補完しない |
| 不足・比較不能 | 無効座標、必要情報の欠測、mask種別の違い、極端な過分割／未分割の疑い | 欠測を0や「良好」へ変えない |
| 実コスト | queue、load、前処理、推論、後処理、測定の時間・取得できたRAM/VRAM | 未来の待ち時間・実GPU並列性を推測しない |

比率の分母は画像面積、ROI面積、mask面積等をフィールドごとに明示する。画像edge算出法、解像度、近傍幅、極小領域閾値は`measurement_profile`に固定し、run後に有利な値へ変更しない。これらの数値は第25節で初期比較課題とともに基準固定する。

全maskの生データはローカル保存し、Jevへは全体統計と有限の領域要約を渡す。要約上限・抽出規則・省略件数を記録する。領域要約の上限を超えても、元の候補一式を黙って別物へ変えない。

### 7.2 追加測定

候補間の重なり対応、境界の不一致、追加の高解像度測定等を、標準測定と別jobとして追加できる。初回評価はこのjobを待たない。新しい認識モデルを追加する必要はない。

候補間測定を実装する場合は、2候補以上が利用可能になった時点から、同じtaskのmask集合に対する定義済み比較を実施する。多対一・包含・未対応を識別し、単一IoU平均に潰さない。計算上限を超えた比較は`NOT_MEASURED_CAPACITY`として示す。

複数モデルが同じ分割を返したことは独立した真実の票ではない。不一致は再検討材料であり、多数派を自動的に正解としない。

## 8．候補固有測定と共通根拠の版 [D]

### 8.1 比較可能性の二層

初期比較の共通根拠E0は、同じK、task、共通画像特徴、測定仕様、公開境界から成る。各候補のmask一式と、**その候補の初回標準測定**は不変の候補記録として束縛する。標準測定は通常コードが計算し、候補自身の主張とは分ける。

この分離は「新しい測定を無視する」規則ではない。次の区別によって、候補到着のたびに無関係なframeや評価を一斉失効させないための設計である。

| 到着した内容 | 版の扱い |
|---|---|
| 別のmask一式と、その初回の標準測定 | 新しい不変候補として追加。既存候補の共通E0に新たな比較材料を加えなければ、E0のまま評価可能 |
| 既存候補に対する新しい測定・測定訂正 | 当該比較scopeの根拠を新版にする。影響候補を再評価 |
| 他候補を含む不一致一覧・合意度・比較結果 | Jevへ新たな材料を提供するので根拠新版。評価対象集合のdigestも保存 |
| 新しい原画像・別時刻 | 第一版では別のframe decision_slot。時点間対応として同じランキングへ混ぜない |
| Jevの点数、勝者、言い換えた説明 | 画像根拠の追加ではない。再入力して自己強化しない |

候補測定digestは各`EvaluationTask`に含め、評価後に同じIDの測定値を上書きしない。既存候補の値を増やしたのに「別候補を追加しただけ」と呼び替えることは禁止する。

### 8.2 比較key

`run / analysis_generation / frame_id / task_version / decision_kind / evidence_version / measurement_schema / rubric_version / renderer_version / evaluator_model_version / validation_policy`が一致する評価だけを比較する。候補ごとのmeasurement digestも評価と一緒に固定する。

同じ一式でも別model・rubric・根拠で再評価した値は別系列である。Choiceなど候補集合に依存する評価は初期選抜に使わず、候補単位の固定基準Scoreを出発点とする。[S2 第5節]

### 8.3 更新範囲と有限性

追加材料の依存から、影響するframeと候補を決める。主勝者だけでなく必要な不採用候補も再評価する。共通材料が全候補へ影響する場合は当該frameの全3〜4候補が対象。画面選択、ログ追加、別runの更新は根拠更新ではない。

短時間の複数追加を一つのsnapshotへまとめることは可能だが、有限の締切を持ち、全jobの終了待ちへ変えない。予算・snapshot上限に達した追加は記録し、未評価材料があることを表示する。旧評価を最新と偽装しない。

## 9．Jev評価：主表示の品質とユーザーの4軸を分離

### 9.1 評価の入口

Jevは、ローカルで抽出した限定的な材料の範囲で判断する評価器として設計する。原画像を見た品質保証とは扱わない。具体SDK・model・wire形式は公式仕様と実環境の照合後に固定する。旧候補`typesafe-sdk 0.7.0 / jev-1.13.0`は[H]であり、最新版・利用可能・互換確認済みではない。

評価入力は短い目的、mask一式の匿名候補ID、測定値と意味、不足、共通根拠、必要な実コスト。model名、S/A/B/Cの評判、正解、過去のJev得点、無関係な会話・全run履歴を入れない。モデル名・device等はローカル監査に残す。

### 9.2 五つの評価項目 [D]

ユーザー指定の4要素は維持し、主表示を選ぶための**分割適合性**を別に追加する設計案である。4軸を単純加算した「総合信頼度」にはしない。

| ID | 表示名 | 高い値の意味 | 主表示との関係 |
|---|---|---|---|
| Q | 分割適合性 | 提供された根拠と観測目的の範囲で、この一式を現在の分割として使うことを支持 | 主表示の既定選抜軸 |
| A | 残る曖昧さ・矛盾 | 未解決・矛盾・区別不能が多い | 高いほど良質とはしない。診断・再確認対象 |
| R | 追加処理の解決見込み | 再分割や測定追加で、指摘した問題を減らせる見込み | 現在の品質とは別。第一版では実行せず記録 |
| I | 観測目的への重要性 | この一式の領域を詳しく理解することが目的に関係する | 評価内訳。品質の代替ではない |
| C | コスト・待ち時間との適合 | 現在の予算・実測条件に照らして利用上の制約に適合する | 実時間・資源の実数を併記。主品質へ隠れて混入させない |

Aだけは「最大が最良」ではない。各軸の最高・最低の候補を切替表示できるが、診断閲覧を主採用に見せない。Rが高い候補を「最も正確な分割」と表示しない。

### 9.3 尺度・採用policyの初期案

Scoreは記述式5段階の0〜4を初期案とする。Qの段階意味は以下。[D]

| Q段階 | 意味 |
|---|---|
| 0 | 目的との明確な不整合や、提供根拠が示す重大な問題がある |
| 1 | 利用を支持する根拠が乏しく、問題が優勢 |
| 2 | 根拠不足・曖昧さにより適合性を支持しきれない |
| 3 | 提供された根拠は用途への適合を支持し、重大な矛盾が見られない |
| 4 | 目的に関連する具体的な測定根拠が、用途への適合を強く支持する |

A/R/I/Cにも別の記述基準を持ち、同じ数値でも異なる意味であることをUIに示す。分布・confidence・Score・実時間・真の品質を混ぜない。主表示の初期下限`Q >= 3.0`はv0.2の閾値方針を用途変更して具体化した**実験設定案**であり、vendor保証や正答率ではない。各rubric全文・尺度のAPI表現・欠測時の扱いは実装基準固定の対象。

第一案は1候補・1根拠snapshotに対して5問を独立評価し、APIが当該形を正式に支えるなら1要求へまとめる。同じ候補の5問をまとめても、他候補の完成は待たない。wire契約が異なる場合は同じ論理suiteを分割し、要求数・質問数の予算を変更前に再計算する。

### 9.4 有効性

envelopeの参照・世代・model・rubric、question対応、必須値、有限数値、範囲を検査する。Qが有効で診断軸だけが無効なら`PARTIAL_DIAGNOSTICS`とし、Qの採用可能性と個別軸の欠測を分ける。envelopeが無効なら全suiteを隔離する。

Scoreと分布の検査は採用した公式契約を根拠にする。旧設計の`strict_numeric_v1 / 1e-8`は検討履歴として残すが、現APIの丸め仕様・実応答を未確認のまま普遍の保証値にしない。採用する検査policyと許容値は実送信前に固定し、rawと独立検算を保存する。無効値を期待値へ黙って置換しない。整合未解決なら無効／未確認とし、採用可能な実評価がない状態を完成にしない。

## 10．採用・重畳・後着改訂

### 10.1 一式単位の主表示 [D]

形式・参照・世代が有効で、現在の比較keyに対するQが採用条件を満たす候補から、最大Qを主表示にする。最初の適格応答で開始し、全解析・全評価の終了は待たない。全候補が不適格なら「Jev採用なし」。未評価候補の手動プレビューは可能だが、採用表示と分離する。

後着上位へ改訂し、下位では主表示を維持する。同点は現在の採用を維持し、採用が無い場合はモデル名に依存しない候補内容digestの固定順を使う。scoreの後付け丸めで同点を作らない。UI描画順や帯ラベルをwinner選択に使わない。

A/R/I/Cの指標別表示は別viewとし、主winnerを変更しない。主軸や閾値を比較したい場合は別のpolicy版としてReplayまたは新runにする。実行中に好都合な規則へ書き換えない。

### 10.2 fixtureで固定する動作例（実測ではない）

| イベント | 状態 |
|---|---|
| Sが完成しJev送信、続いてAも送信 | B/CやSの評価終了をAの送信条件にしない |
| AのE0評価Q=3.2が先に返る | Aを暫定表示 |
| SのE0評価Q=3.6が返る | Sへ改訂。予想速度帯と関係なく実評価を使用 |
| BのE0評価Q=3.1が返る | Sを維持。Bの結果は保存 |
| 追加測定でE1になる | Sを旧根拠暫定と表示し、必要候補をE1で再評価 |
| CのE1評価Q=3.3が最初に返る | E1で初めて適格なCを暫定表示。Sの旧3.6との比較ではない |
| SのE1評価Q=3.8が返る | 同E1でSへ改訂 |

Q=3.8は画像の正答率ではない。自然実行で同じ順序・改訂が起きるとは予告しない。

### 10.3 状態とtransaction

`UNEVALUATED / EVALUATING / EVALUATED / PROVISIONAL / SUPERSEDED / BELOW_THRESHOLD / STALE_EVIDENCE_PROVISIONAL / INVALID / CANCELLED / UNAVAILABLE`を区別する。

重い測定・通信はtransaction外。短い状態更新で、世代・比較key・重複・現在勝者を再確認し、評価、SelectionRevision、outboxを整合して保存する。同じeventの再配送は一回だけ適用する。DBに確定保存したことと、分割が真実として確定したことは別。

## 11．根拠更新・再評価・公開順

新しい共通根拠E1を作ると、影響scopeの旧評価を最新ランキングから外す。旧表示は根拠が古いことを明示して保持するか、保留にする。E1の最初の適格評価から新版の表示を開始する。未着の旧勝者に「勝った」とは記録せず、理由を`FIRST_ELIGIBLE_IN_NEW_EVIDENCE`とする。

E0へ送信済みの応答がE1作成後に到着しても、E0の記録として保存するだけで、E1の主表示へ上書きしない。過去の当時状態Replayでは利用できる。独立した別frameは止めない。

再評価上限・予算・保持不足は`REASSESSMENT_NOT_SCHEDULED`等の理由付き状態にする。材料が増えたのに再評価できなければ「最新根拠で評価済み」と表示しない。既存候補の再評価で良い点が出るまで再試行する運用は禁止。

同材料のretryは同じ論理評価のattemptであり、独立票にしない。最初に受理された有効attemptを採用用とし、遅れて到着したduplicateから高い点だけを選び直さない。明示的な再採点のばらつき研究は別run・別評価epoch。

根拠に候補間比較が含まれる場合、一本除外した構成では根拠も変わり得る。四本構成の得点を、そのまま三本構成の評価として転用しない。必要な再評価は実行条件内で別計数する。

## 12．時刻・並列処理・有限資源

### 12.1 キーフレームと再生

要求した秒数、実際にdecodeしたPTS/sample、公開時刻を分ける。可変frame rateや重複PTSを平均FPSだけで一意化しない。再生中の動画と解析済みキーフレームは独立表示できる。

自然再生・表示対象変更・一時停止は、公開済みKの解析を失効させない。seekのdecode取消しと解析generationを分ける。素材切替・reset・明示解析停止は旧generationを失効させる。EOF／キーフレーム集合の受付終了は有限drainへ進む。元時刻のmaskを現在の別frameへ重ねない。[S2 第6節]

第一版では選択画像を独立に処理し、未来frameを過去の候補採点に自動投入しない。オンライン相当の測定、手動の対話的利用、保存画像のオフライン実験をmodeで区別する。

### 12.2 実行構成

controller、decoder、segmenter worker、共通測定、Jev lane、state writer、UI投影を分離する。各jobの完了通知を完了順に収集する。制御HTTPが推論・Jev待ちを同期的に抱えない。

同じGPUの3〜4経路は、独立jobとして投入できることと、GPU kernelが実際に3〜4個同時に実行されることを区別する。実同時性は実測なしに宣言しない。CPU使用、複数process、共有backendの選択は実環境照合後に決める。

| 資源 | 初期設定案 [D・実行未承認] |
|---|---|
| 比較lane | 3または4。一経路対照も別modeで可能。各lane同時1jobを出発点 |
| active keyframe | 初期2。相互に候補を混ぜず、容量不足は受付前に表示 |
| decoder | 1worker、入力descriptor最大16 |
| CPU測定 | 同時2、待機descriptor最大32 |
| GPU permit | 安全なsmokeは1。比較では1〜4の範囲で実測し、許可された値をconfigurationに固定 |
| Jev | 同時2要求、待機64論理suite。画像poolとは独立 |
| candidate | 一比較frameあたり3〜4一式。mask数・bytes上限はモデル別に宣言 |
| UI | 最近200履歴行、古い行は頁取得。差分適用の上限案10Hz |
| 保存 | 研究rootの総容量・frame/mask上限をprofileで固定。満杯時に採用結果や旧runを黙って消さない |

同じbackendで複数重みを扱う場合も、共有可否とthread/process安全性を確認する。各スレッドが無制限にモデルを複製してVRAMを消費しない。OOMで解像度やmodelを自動縮小して同じ構成の成功にしない。

### 12.3 公平性と時計

job待機・model load・前処理・推論・後処理・測定・Jev・保存・UIを別計測する。帯順の投入バイアスは記録し、構成比較の繰返しでは順序を均衡化する。単一の遅いjobが無関係なframeの公開を止めない。

期間は比較可能な単調時計で測る。process間・ブラウザーとserverの時刻を未検証のまま引き算しない。GPU時間は同期と測定方法を記録し、CPUからのenqueue時間をGPU完了時間にしない。得られない値は未測定。

## 13．保存・エラー・正常終了・Replay

### 13.1 全runを後から比較できる保存

第一ゴールの反復比較には、利用者が設定した研究保存rootが必要。runごとにconfig、入力参照、全候補mask、測定、全評価、イベント、時間、失敗、使用量を保存する。勝者だけ保存する方式にはしない。

研究保存は新repoと独立した新側所有rootを使い、原動画・frame cache・モデルcache・DB・一時ファイルの所有関係を分ける。原動画を丸ごと複製するか、必要なキーフレームだけ保存するかをprofileに記す。終了時に保存runを消さない。期限・容量・削除操作はUIとmanifestに明示する。

保存未設定の一時modeも可能だが、終了後の全run比較や完全Replayを保証しない。期限切れ・削除済みは`UNAVAILABLE`。チャット新設やアプリ再起動で保持期限を延長しない。[S2 第10節]

### 13.2 障害と再送

Jev OFF、429、timeout、認証エラー、数値不整合、空結果、OOMは別状態。通信失敗を0点にしない。無効評価の候補を隔離し、他候補の表示・再生・停止を継続する。

retryの責務は一箇所。SDKとアプリで二重に再送しない。初回＋最大1回を初期案とし、採用SDKで内部retryを制御できる方法を確認する。送信前に要求・質問・bytes・費用の予約を原子的に行う。到達不明のtimeout予約を勝手に返さない。401/403や継続障害はcircuit停止とし、無限の自動再接続を行わない。

### 13.3 原子的記録と回復

mask大容量ファイルは新側の一時pathへ書いてから確定し、内容hashとDB参照を整合させる。SQLite transaction内で推論や外部通信をしない。クラッシュ後は自分の孤児runだけを検査し、部分完了・欠落を表示する。旧アプリのDB migration・cache回収を実行しない。

### 13.4 正常終了

受付停止 → 取消しまたは有限drain → 所有worker停止／join → HTTP・Jev client・DBをclose → 一時領域だけ回収 → 保存runと終了記録を検証、の順とする。native処理の強制終了は`FORCED_SHUTDOWN`であり正常終了PASSにしない。全Python・全Chromeを一括killしない。

Replayは保存データとイベントの閲覧であり、推論・Jev送信は0回。「当時の公開順」「現在の根拠での改訂結果」「別policyの反実仮想Replay」を区別する。新しいJev採点はReplayではなく別の再評価runとして記録する。

### 14.3 キュー詰まり・待機数の視覚表現

第一版のUIでは、各処理段の**待機詰まり**を明確に表示する。少なくとも、②領域分割候補、③共通測定、④Jev評価キュー、⑤採用・後着改訂、⑥保存／Replayについて、次を可視化する。

| 表示項目 | 意味 |
|---|---|
| `待機数` | まだ処理開始していないjob数または評価数 |
| `実行中数` | 現在処理中のjob数 |
| `完了数` | このKまたはrunで完了したjob数 |
| `保留／失敗数` | 無効応答、失敗、取消しで次段へ進まない件数 |
| `混雑状態` | 通常／注意／混雑／飽和の状態。色で表現する |

混雑状態は、少なくとも以下のように表示する。

| 状態 | 代表色 | 意味 |
|---|---|---|
| 通常 | 青〜緑 | 待機が軽微で、許容範囲内 |
| 注意 | 黄 | 待機が発生し始め、遅延が見え始めている |
| 混雑 | 橙 | 待機数または待機時間が大きく、後続表示へ影響している |

待機の表示は、件数だけでなく**継続時間**も別途出せるようにする。第一版では、少なくとも`最古待機秒数`または`平均待機秒数`のどちらか一つをbox内またはtooltipで示し、件数0でも長時間の停止が埋もれないようにする。しきい値は第11節・第12節の資源permit／deadline設計に従い、色の境界値をrun定義へ記録する。

### 14.4 第一版のUI境界

第一版の主題は、**固定された3〜4laneの領域分割比較**を分かりやすく見ることである。したがって、UIには次を入れない。

- スレッド数の追加・削除操作
- 実行中にlane数を増減する操作
- 領域分割やその他画像処理のアーキテクチャを、その場で編集・差し替えする操作
- 任意Python、shell、任意URL、任意model取得を伴う自由編集

設定読込や実行ボタンは残してよいが、第一版で扱うのは**承認済みの固定構成**または**保存済み比較構成の読込**までとする。未承認backendの追加、laneの新設、worker数変更はアプリ運用時の自由編集にせず、別の実装／設計変更として扱う。

### 14.5 重畳と操作の正しさ

maskは勝者の元Kだけに重畳する。異なる元時刻の動画枠へ位置を転写しない。透明度・輪郭／塗り・候補切替は表示設定であり、解析結果を変更しない。候補間で色が同じでも同じ物理対象という意味にはしない。

ログは最新上、閲覧中のscroll anchor・選択を保持する。フィルタ群を必須操作にしない。詳細は必要時に開く。長い履歴の全DOM再生成は避ける。

`RevisionCommitted`と`UIRevisionApplied`を分ける。ACKはUI状態・描画処理へ適用した証跡であり、人が視認した保証とは別。画面品質は主要シナリオの実ブラウザー確認で検査する。非表示tabや描画省略のため未表示の改訂を、全て可視だった成績へ混ぜない。

## 15．同じ動画を反復する実験設計

### 15.1 固定するもの

dataset・動画hash、キーフレームの実PTS／pixel hash、task、対象クラス・粒度、model重みrevision、前後処理、入力解像度、precision、mask生成設定、測定profile、rubric・Jev model、資源permit、cold/warm、試行順、実装HEAD、保存・予算を記録する。

同じアーキテクチャでも、重み・設定・解像度・backendが変われば別configuration。比較単位を「モデル名だけ」にしない。warmの定義とwarm-upの処理量を記録し、cold時間を失敗として除外しない。

### 15.2 試験を三種類に分ける

| 種類 | 固定／変更するもの | 得られる結論 |
|---|---|---|
| 選抜policy比較 | 同じ候補・公開済み根拠・保存評価・到着記録で、全件待ち／完了順等を比較 | 保存された同じ仕事量での方針差。実機を別に走らせた速度差ではない |
| 構成の実測比較 | 同じK集合へ、三本／四本／単独／一本除外等を実際に再実行 | 資源競合・load・失敗・実時間を含むその構成の結果 |
| 評価器の比較 | 同じ測定入力でJevと固定規則を比較。課金やJev待ちも区別 | 非同期構造だけの効果と、Jevによる候補選抜の効果を分離 |

初回は登録した全jobを完走させる。低評価だから実行中の推論を止めて計算を節約する方式は別研究とする。全件待ち対照のbarrierは当該K・当該根拠epochの有限候補だけに適用し、通常modeやsession全体へ波及させない。[S2 第13節]

一本除外したときの実時間を、四本runの時間から単純に引き算しない。候補集合に依存する追加根拠がある場合、評価値の流用可能性も第11節で判定する。

### 15.3 組合せの探索を有限にする

全モデルの全組合せを総当たりしない。承認されたadapter群から少数構成を登録し、単独基準→三本→四本／一本除外→必要な差替えの順に、各batchのplanで比較する。上限内の通常反復はアプリ操作で行い、毎runのCodexチャット新設・コード修正・依頼文作成を不要にする。

同じ動画内でも調整用キーフレームと最終確認用を分け、確認用を見た後に構成や尺度を最適化した場合は新しい調整回として記録する。正解なし・動画一本の場合の一般化限界を明示する。

## 16．測定項目と「良い組合せ」の判定

| 観点 | 指標・記録 |
|---|---|
| 初回利用 | 最初の有効mask、最初のJev適格候補、最初の主表示までの時間を分ける |
| 途中品質 | 独立品質判定がある場合の時間推移、悪い表示の継続、評価不能時間。Jev点数で品質を代用しない |
| 改訂 | 全切替、良化、悪化、同等、判定不能。数が多いほど良いとはしない |
| 最終品質 | taskに適した領域一致・境界・過分割／未分割、人手比較。正解がなければ数値の正答率は不明 |
| 待機・資源 | queue/load/前後処理/推論/測定/Jev/保存/UI、RAM/VRAM、cold/warm、OOM・timeout |
| 評価器 | 有効／無効率、欠測、再評価回数、要求・質問・bytes・token・取得できた費用 |
| 構成の追加価値 | 追加モデルだけが改善したK、増えた競合・待ち、除外時の差 |
| 再現性 | 試行ごとの分布、欠落・中止を含む分母、順序・条件差 |

人手確認・真mask・品質ラベルは別管理し、解析器とJevに渡さない。評価担当にはモデル名・帯・Jev得点を必要に応じて隠し、同じ基準で比較する。品質未評価のrunは速度・動作比較には使えても、品質勝者の根拠にはしない。

Codexは、まずtask・条件が比較可能な群に分け、初回表示、最終品質、途中の悪化、資源・費用を別に判定する。「総合的に最良」を出す場合は利用目的と選好条件を先に明示する。必要なら速さ重視・品質重視・資源重視を分け、優劣不明・同等・条件付きも残す。

Jev自身が付けた高得点の組合せを、そのまま正しい組合せと結論しない。単独モデルが十分よい結果でも、予定した非同期選抜の検証を中止する根拠にはしない。逆に、Jevが不要・悪化という測定結果も隠さない。[S2 第13節]

### 19.3 計数単位と予算

論理suiteは候補×根拠snapshot×rubric版×評価epoch。question数とHTTP送信数を別に数える。5問を1HTTPにまとめる構成でも、5問として記録する。retryも実送信として数え、チャット新設やアプリ再起動で残量を回復させない。

4候補について、各到着後に全既存候補を新根拠で再評価する単純例は、1+2+3+4=10 suite/K。5軸なら50問/K。これは計数例であり、必ず10回評価する仕様でも実測値でもない。共通根拠が変わらなければ初回は4 suite/Kで済む。

| 枠 | v0.3の初期案 [D・未承認] |
|---|---|
| SC00 | 静的実査・事実対応のみ。model/依存取得、実推論、Jev、remote操作は0 |
| SC01 | fixture専用。実動画・実model・実Jevは0 |
| 初期ローカルsmoke | 選定した3〜4経路、少数K。model loadと並列構成を段階確認。具体job数は採用manifestで固定 |
| 実Jevの有限確認 | 合計128論理suiteまで、最大5問/suiteを想定 |
| 実送信の上限案 | retry込み256 POST・1,280問、同時2、1要求body最大32KiB・累計8MiB |
| 後段UI・出力試験 | 保存済み記録／fixture Replayを既定。追加送信0、必要な実確認は残量内 |
| 比較batch | N構成×N試行×Nキーフレーム×Nlane、再評価計画を開始前に計算。上記枠に収まらなければ実行前に計画を縮小または別承認 |

上記は旧256問枠を維持したまま5軸へ増やしたものではなく、**論理suiteと質問数を再設計した未承認案**。実装時間やチャット時間の上限とは別。実GPUジョブ、load/warm-up、Jev、再評価、保存容量の各総量を一枚で計算する。

費用上限は実行時の確認済み価格・token上限／usage契約に基づいて予約する。旧価格を使って請求保証しない。価格やtoken見積りの境界が未確定なら、費用は未確認とし有料送信開始条件を未充足にする。呼出し・bytes制限はアカウント全体の課金上限ではない。

### 19.4 通常利用・保持

通常利用は自動試験とは別profile。許可された構成・送信・保存・動画範囲内なら、ユーザーが動画を選んで反復でき、毎回名称・秒数・grantをチャットに提出しない。新しいモデル取得・送信先・上限増加・範囲外素材・追加権限だけを再確認対象にする。

研究保存は各runの期限・容量を表示し、後のCodex比較日程を満たす値を決める。旧7日／終了時削除を無検討で引き継がない。期限切れ前の延長は明示設定変更として残す。終了時に削除するのは一時領域であり、保存runは設定どおり保持する。
